# A ComputeConfig of the SMOSolver asking for the exact solution path, i.e.,
# the samples added to the data set are learnt by growing their multiplier
# from zero while every other dual index is kept at its own optimality
# condition, rather than by iterating from the previous solution.
#
# It is SMOCfg.txt with the two entries below changed, and says so through
# the cascade-override mechanism ('*SMOCfg.txt +') instead of repeating the
# whole ComputeConfig: whatever is not named here is what the base gives.
#
# - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
# - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

# the base ComputeConfig, plus the overrides below - - - - - - - - - - - -
*SMOCfg.txt +

1  # f_diff == 1 ==> only the entries below are changed

1  # number of integer parameters

# now all the integer parameters
intSMOPath  1  # the samples added are learnt by walking the exact solution path

1  # number of double parameters

# now all the double parameters
dblSMOTol  1e-10  # the walk is exact, so the iteration it is compared with
                  # has to be asked for a solution of the same quality, or
                  # the comparison is between two different problems

0 # number of string parameters

# now all the string parameters
# [none]

0 # number of vector-of-int parameters

# now all the vector-of-int parameters
# [none]

0 # number of vector-of-double parameters

# now all the vector-of-double parameters
# [none]

0 # number of vector-of-string parameters

# now all the vector-of-string parameters
# [none]

# the "extra" Configuration slot is left out on purpose: an override block
# that ends here keeps the one of the base
